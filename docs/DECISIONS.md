# 已确认的产品决策

更新日期：2026-07-30

## 产品与用户

- 产品暂定名为“向前 · 求职工作台”。
- MVP 面向校招及毕业 0—3 年求职者。
- 首批重点岗位类别为运营、产品、法务。
- 首版中文优先；岗位专属简历优先输出保留原模板的 Word，PDF 第一阶段由用户在 Word 中另存。

## 数据与权限

- 通用岗位与投递数据保存在 Web 产品中。
- 简历、身份证件等敏感个人资料优先保存在本地插件中。
- 不要求用户向 Agent 提供招聘网站密码、验证码或 Cookie。
- 用户自行登录招聘网站，插件只在用户主动操作时读取当前页面或辅助填表。
- MVP 不自动完成最终投递提交。

## 岗位来源

- MVP 不建设全网岗位聚合和持续同步能力。
- 岗位由用户主动收录，支持链接、JD 文本、截图和插件一键保存。
- Agent 提取结构化岗位字段，用户确认和修正后才创建记录。
- 记录“在哪里看到岗位”；投递方式在用户标记已投递时再可选记录。
- 当前可用版本先只开放“粘贴 JD 文本”，优先打磨字段提取准确率和岗位记录闭环。
- 岗位链接、截图上传和插件保存保留为后续入口；在真实能力接入前显示“暂未开放”，不得进入空白确认页。

## 岗位状态

- 新收录岗位默认状态为“待投递”。
- 岗位状态与简历、Cover Letter 等材料准备进度分开显示。
- MVP 状态为：待投递、已投递、面试中、Offer、已结束。
- 用户手动标记“已投递”，系统记录投递时间并停止待投递提醒。
- 待投递岗位收录超过 24 小时后显示简洁的站内提醒。

## 简历定制

- 个人档案保存不可虚构的事实来源；简历中心管理主简历和岗位专属版本；岗位工作区负责针对当前 JD 发起优化。
- 当前 MVP 只支持粘贴简历文本，PDF 上传和复杂排版后续开放。
- 主简历、匹配分析和岗位专属版本保存在当前浏览器，不上传到业务数据库。
- 只有用户主动点击“开始 AI 匹配分析”时，才临时发送当前 JD 与主简历；产品服务端不保存请求正文。
- AI 分析仅对已登录且在费用白名单内的 ChatGPT 账号开放；公开页面仍可浏览。模型服务当前使用 DeepSeek，通过产品后台私密 API Key 调用；登录身份不代表模型额度。
- 所有修改建议必须同时绑定简历原文和 JD 原文；新增数字会被拒绝，其他表述仍须用户逐条确认。
- 采纳建议只创建岗位专属新版本，不覆盖主简历。
- AI 服务失败时必须区分额度、密钥、模型配置、超时和结果校验问题；生产日志不得记录 JD 或简历正文。不得在失败后静默将同一份 JD 或简历发送给第二家模型服务。
- 主简历只在简历中心录入一次，岗位工作区直接读取，不再要求逐岗位重复粘贴。
- 当前支持在浏览器本地解析 `.docx` 主简历；原 Word 文件不上传，解析出的文本允许用户继续核对和编辑。
- 简历定制采用双栏交互：左侧逐条决定是否采纳，右侧显示实时同步的完整岗位简历并允许直接编辑。
- 保存操作创建岗位专属版本；原始 `.docx` 文件只保存在当前浏览器的 IndexedDB，不上传业务服务端。
- 第一阶段通过修改原 `.docx` 的正文 XML 生成岗位专属 Word，保留原文件的样式、表格、分栏、图片、页眉页脚和页面设置；用户在 Word 中检查后另存为 PDF。
- 为避免破坏模板，当前只允许安全回写段落内部的文字修改；如果右侧新增或删除整段，系统明确阻止原模板导出并提示用户修正。
- 浏览器打印入口保留但标注为“纯文本 PDF”，不再暗示其能够还原原简历排版；自动 PDF 转换留待后续专用文档服务实现。
- 未建立真实候选人样本、统一评价口径和验证集前，不展示“高于同类候选人百分比”等排名；匹配概览只使用可追溯的简历和 JD 证据。
- 工作台提供 ChatGPT 登录、退出和切换入口；切换 ChatGPT 身份不会切换或补充产品后台的 API Key 额度。

## 文档与版本控制

- 每完成一个相对独立模块，建立一份 Obsidian 兼容 Markdown 归档。
- 每次归档后建立对应 Git 检查点。
- 项目文档和 Git 历史是跨 AI 交接的事实来源。
