# 项目归档与 Git 工作流

## 目标

让产品上下文独立于任何单一 AI 聊天工具。即使更换 Codex、Claude Code、
Cursor 或其他工具，也可以通过项目文件恢复完整上下文。

## 什么时候归档

满足以下任一条件时建立 Markdown 归档：

1. 一个产品模块的目标、流程和边界已经确认；
2. 一组重要产品决策已经获得确认；
3. 即将进入下一模块或进行较大代码调整；
4. 原型完成一次可独立演示的更新；
5. 用户明确提出“归档”或“定稿”。

普通探索、尚未确认的想法和临时排错不单独归档。

## 每次归档包含什么

- 本模块解决的问题；
- 已确认的产品决策；
- 核心用户流程；
- 关键交互与文案；
- 数据字段或状态变化；
- 权限、安全和隐私边界；
- 已完成与尚未完成；
- 下一步建议；
- 与上一个版本相比的变化。

## Obsidian 规则

- 文件保存在 `docs/archives/`；
- 文件名使用 `YYYY-MM-DD-topic-version.md`；
- 使用 YAML frontmatter 记录日期、状态和标签；
- 一份归档只对应一个相对独立的模块；
- 文档使用普通 Markdown，不依赖特定聊天产品的格式；
- 不复制未经清理的聊天日志、工具输出、密钥或临时访问凭证。

## Git 检查点

每次模块归档后执行：

1. 检查本次变更范围；
2. 运行与风险相称的构建或测试；
3. 检查是否误包含个人信息、密钥、缓存或依赖目录；
4. 更新对应 Markdown 归档；
5. 创建一条聚焦该模块的 Git 提交。

推荐提交信息格式：

```text
feat(module): 简短说明
docs(module): 归档模块决策
fix(module): 修复具体问题
```

## 跨 AI 交接

新的 AI 开工前应依次阅读：

1. `README.md`
2. `outputs/MVP_PRD_V0.1.md`
3. `docs/DECISIONS.md`
4. 最新的 `docs/archives/*.md`
5. 与当前任务直接相关的代码

聊天记录只作为辅助材料，项目文档和 Git 历史才是事实来源。
