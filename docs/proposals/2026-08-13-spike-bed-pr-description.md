# PR 标题

`spike: 验证经历级简历编排与专属偏好多岗排序`

# PR 描述

## 这是什么

这个 PR 新增两个保持在 `/spike` 命名空间内的可运行实验，并带回几项可独立审阅的 AI 运行时改进。

第一条实验回应一个很直接的体验问题：现有“对着 JD 改简历”虽然能给出有依据的局部建议，但用户仍可能感觉“改了跟没改一样”。原因不只在模型或措辞，也在输出契约：一张卡只要求模型提出一条修改意见，容易得到多个正确却零散的 bullet 补丁。

`/spike` 改为按“经历单元”输出：每张卡是一段建议进入投递版的实习或项目经历。用户可以保留原文、接受针对 JD 的重写、决定前置/中位/后置，或把该经历标为本次不放。这里的 `omit` 是岗位版本的取舍，不是对经历本身的否定。

第二条实验是 `/spike/rank`：让用户提供自己的择业 SKILL，以门控、权重、0/5/10 锚点、软性扣分和并列规则，对 2—6 个岗位给出可解释的相对排序。它回答“按我的偏好哪个更值得优先”，不与“我的经历是否足以支撑这个 JD”的简历匹配分混为一谈。

## 明确边界

- 不进入主导航，不替代已确认的 Step 1 差距分析；
- 不改变 `resume_quote` / `user_confirmed` 的事实来源边界；
- 不覆盖主简历，排序页也不写回主站岗位状态；
- 不将简历匹配与择业偏好合并成一个分数；
- 不在仓库内置某位贡献者的个人择业框架。用户可用访谈协议在外部 Agent 中生成自己的 SKILL，再上传或粘贴到测床。

## 同时包含的工程改进

- 长推理请求的可配置超时；
- 模型因 token 上限截断 JSON 时的显式检测与报错；
- 合并重复的证据缺口与追问；
- 本地 spike run log，供真实样本复盘；
- 路由、契约、排序纯函数与日志链路测试。

## 建议审阅方式

1. 用同一份真实 JD 与简历，对比主站建议与 `/spike` 的经历级输出：是否出现真实、可感知的经历取舍、排序与叙事差异？
2. 检查这些差异是否仍受原始事实约束，且 `omit` 的语义是否清楚。
3. 用一份专属择业 SKILL 比较 2—6 个相近岗位：排序理由是否严格对应规则；改变权重后，排序是否以可解释的方式变化。
4. 将“可回流工程能力”“spike 页面”“主站 Step 2 契约”分开决定，不要求一次性全量合并。

## 需要产品负责人确认的开放问题

1. 经历单元、取舍与排序，是否比现有建议卡更接近用户对“AI 对着 JD 改简历”的期待？
2. 如果成立，未来 Step 2 应以它为默认形态，还是与 bullet 级精修并列为“经历视图”？
3. 专属偏好多岗排序是否继续保留为独立 spike；若未来进入主站，入口更适合放在岗位列表多选对比，还是个人偏好设置？
4. 哪些工程改进可先回流主线，哪些继续留在 spike 中积累真实样本？
