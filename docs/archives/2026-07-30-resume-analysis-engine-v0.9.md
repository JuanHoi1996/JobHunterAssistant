# 简历分析引擎 V0.9

## 本模块解决的问题

V0.8 的简历分析虽然能够保证原文引用和禁止新增数字，但提示词要求每条建议只修改一个连续片段，模型又在一次调用中同时完成 JD 理解、证据匹配和改写，最终容易退化为少量近义词替换。

用户需要的不是表面润色，而是识别原简历中的独特经历、方法、复杂度、结果与可迁移能力，再根据 JD 重建完整表述。

## 已确认方案

当前不等待外部简历修改 Skill，先完成两阶段分析引擎，并为未来蒸馏方法论预留扩展位。

### 第一阶段：岗位与候选人分析蓝图

模型输出：

- JD 能力优先级：核心、重要、加分；
- 每项能力的 JD 原文和业务解释；
- 原简历可放大的亮点；
- 每个亮点绑定的一处或多处简历原文；
- 可迁移能力；
- 当前证据缺口和具体追问。

蓝图先经过服务端原文校验。不存在于 JD 或简历中的引用会被删除，未经校验的蓝图不会直接进入改写阶段。

### 第二阶段：整条经历重写

模型基于真实 JD、完整简历和已校验蓝图生成：

- 匹配项；
- 证据缺口；
- 待用户补充的问题；
- 3—6 条优先级明确的改写建议；
- 完整 original；
- 多处 sourceEvidence；
- revised；
- 改写类型；
- 改写原因；
- 质量自检。

建议优先重写完整经历表述，目标是重建“目标或问题—行动与方法—产出或结果—JD 关系”，不以替换少量词语作为有效提升。

## 多证据真实性校验

V0.9 允许一条改写整合简历不同位置的事实。例如同一项目中分散出现的：

- 用户反馈处理数量；
- 标签或分析框架；
- 跨团队协作；
- 流程优化；
- 量化结果。

每一处都必须作为连续原文写入 `sourceEvidence`。

数字校验由“只能来自 original”调整为“可以来自 original 和全部 sourceEvidence”，因此可以组合真实亮点，但仍不能新增任何未被引用的数字。

## 角色与程度升级拦截

真实接口验证发现，模型可能在没有依据时加入“实时”“熟练”等词。V0.9 新增确定性拦截：

- 主导
- 牵头
- 独立负责
- 熟练
- 精通
- 实时
- 显著
- 大幅
- 成功推动
- 全面
- 深度参与
- 端到端
- 从 0 到 1

只有这些词在引用证据中逐字出现时，改写才能使用。未通过的建议直接删除。

## 前端交互

分析完成后按顺序展示：

1. 分析结论；
2. JD 能力优先级；
3. 原简历可放大的亮点；
4. 已有证据与缺口；
5. 值得向用户追问的信息；
6. 带优先级、重写类型和质量自检的逐条建议；
7. 右侧同步简历草稿。

用户仍逐条决定是否采纳。AI 不直接覆盖主简历。

## Skill 扩展位

`app/resume-methodology.ts` 中保留 `RESUME_SKILL_EXTENSION`。

后续用户蒸馏出简历修改 Skill 后，可以加入：

- 产品、运营、法务岗位的不同评价逻辑；
- 优秀修改前后样例；
- 行业措辞与禁用表达；
- 质量评价量表；
- 追问策略。

Skill 内容必须被翻译为产品运行时规则，不能只安装在 Codex 中，也不能绕过真实性校验。

## 隐私与成本

- 用户点击一次分析会顺序调用同一模型两次；
- 第一轮输出分析蓝图，第二轮输出改写结果；
- JD 与简历仅在用户主动分析时发送；
- 服务端不保存请求正文；
- 失败后不自动转发给第二家模型；
- 两阶段方案会比旧版增加调用时间和 Token 成本，后续用真实样例评估质量收益后再优化缓存。

## 验证

- 构建通过；

- 使用完全虚构的测试 JD 和简历完成真实 DeepSeek 两阶段调用；
- 接口返回 `pipelineVersion: 0.9`，成功输出 JD 优先级、四项亮点、匹配、缺口、追问和整条经历重写；
- 真实调用发现并修复“实时”“熟练”等无依据升级词问题。
