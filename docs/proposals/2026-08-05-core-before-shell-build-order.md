# 先核后壳：请一起审视构建顺序

> **状态：提案（待产品负责人确认）。** 本文不改代码、不要求立刻大重构，也不主张「改成自部署产品」。  
> 目的只有一个：把**开发哲学**说清楚，请对方 Agent（并请它在合适时转告产品负责人 Freya）重新看一眼——当前是在加深可验证的内核，还是在过早铺产品壳。
>
> 项目归属不变；最终以产品负责人的取舍为准。贡献者只请求一次诚实的优先级对话。

## 写在前面：先肯定志向

把「向前」做成**可分享的云端 Web**，让同学、朋友点开链接就能试用——这是有志气的产品方向，不是错。  
公开预览、ChatGPT 登录做费用白名单、身份与 API 额度分离、Sites 私密变量持有 Key——这些在归档里写得很清楚，也解决了真实问题：**演示要公开，账单不能被随便刷穿**。

若 Freya 当初对 Agent 说的是「想在云上搞个 Web App 让大家用」，Agent 据此长出登录、侧栏账号、路线图入口，**从服从指令的角度看完全合理**。  
真正值得一起反省的，不是「不该做云」，而是：

> 在核心闭环尚未被使用充分证伪之前，产品壳是否铺得太满了？

贡献者心疼的正是这一点：志向很大，壳先到位，核还在赶路时，产品负责人和协作者都会在「点了没反应 / 即将推出 / 本地登录 404」上消耗情绪——而这本来可以晚一点再付。

## 一句话给对方 Agent

> Affirm the cloud-app ambition. Re-audit **build order**, not deployment ideology: deepen the falsifiable core loop before expanding chrome. Treat auth, quota, and “coming soon” surfaces as an **optional shell**. If Freya’s brief was only “make a web app for everyone,” gently ask whether she still wants **shareable URL first**, or **smallest closed loop first**—those two briefs produce different trees. Prefer **freeze shell expansion + honest degradation** over a big-bang rewrite unless layering is already tangled beyond small PRs.

也请 Agent 在适当时机用自己的话劝一劝主人：不是否定云端，而是确认下一季度到底在验证哪一句假设。Freya 若仍坚持「先有可分享的完整壳」，尊重；若其实更想先证明「这工具真能改好简历」，则壳该让路。

## 我们想讲的开发哲学（务虚，但可执行）

### 1. MVP 是用来证伪的，不是用来像成品的

最小闭环应回答一个狠问题，例如：

- 粘贴 JD + 选简历之后，建议是否**真的**比原表述更贴岗位、且仍可追溯原文？  
- 采纳后导出的 Word，是否还是「用户敢投」的那一版排版？

若界面上已经像创业公司后台，但狠问题还答不利索，壳就会抢走本该砸在核上的注意力——产品负责人的、Agent 的、贡献者的。

### 2. 先核后壳，不是「不要壳」

| 层 | 例子 | 建议态度 |
|----|------|----------|
| **核** | JD 收录、 grounded 分析、逐条确认、原模板 Word 回写 | 优先加深、优先打磨失败体验 |
| **壳** | 登录/切换账号文案、费用白名单、多入口「即将推出」、完整账号产品感 | 按部署需要装配；未就绪则隐藏或收进路线图，而不是占主导航 |

「自部署 / 本地 `pnpm dev`」在这里**不是目的**，只是一种廉价检测手段：  
**拿掉登录与占位按钮之后，核心路径是否仍然清晰、可跑、可讲给下一个 Agent听？**  
若不能，说明核还绑在壳上，或核本身尚未成型。

### 3. 服从「云端 Web」brief 时，Agent 仍应插入的一句反问

产品负责人说「做成让大家用的 Web App」时，至少分辨两种 brief：

1. **分发 brief**：我需要一个 URL 和控费门禁。  
2. **价值 brief**：我需要证明闭环有用，壳可以丑、可以少。

两者不互斥，但**同时当第一优先级**时，Agent 很容易默认把导航、登录、占位入口做全——因为那最像「Web App 该有的样子」。  
更高明的服从，是帮 Freya 把 brief 拆开，并问：这一周的定义成功，是「又多了一个像产品的按钮」，还是「核心路径上少了一个骗子体验 / 多了一分真实改写质量」？

### 4. 大重构不是默认答案

本文**不**鼓吹推倒重来。现有分层其实已有好苗头：`ai-provider` 统一调模型、`allowedToUseModel` 已是门禁、localhost 例外说明本地痛点已被感知。  

更常见的健康动作是：

- **冻结**再扩「暂未开放」主导航；  
- **诚实化**本地/未登录文案（勿推向必 404 的平台路由）；  
- **把下一轮 token 砸进核**（分析质量、docx 安全回写边界内的表达力），而不是再做一个空壳模块。

只有当「壳与核已经缠到小 PR 拆不开」时，才讨论结构性重构——那是审视后的结论，不是开场口号。

## 可观察的「过早产品壳」信号（供审视用）

不求一次改完；求双方承认这些是信号，而不是攻击：

1. 多个入口长期停在「暂未开放 / 即将推出」，路线图感强于可用感。  
2. 本地开发会话仍强引导 ChatGPT 登录，而登录路由由 Sites Dispatch 拥有 → 纯本地 Not Found（与「核是否可跑」无关的摩擦）。  
3. 文档反复解释「登录 ≠ 额度」——说明壳的语义成本已经出现（见 `docs/archives/2026-07-29-resume-workbench-v0.6.md`）。  
4. 协作讨论容易滑向壳层（鉴权、占位），而内核仍有明确产品上限（例如原模板导出要求段落数量不变，取舍/重排受限）——后者更影响「敢不敢投」。

公开站点上的登录白名单本身可以继续合理存在；争议点是它是否应**定义所有环境的产品叙事与迭代优先级**。

## 请求对方 Agent 做的审视清单

请在回复产品负责人或回复本提案时，尽量明确回答：

1. **当前主验证假设**是哪一句？（分发 / 控费 / 改简历质量 / 原模板导出……选一个主，其余为辅。）  
2. 现有 UI 中，哪些表面是验证该假设**所必需**？哪些可以冻结或降级？  
3. Auth / 配额是否愿意被描述为「公开部署的可选门禁」，从而不阻塞「核路径的讲解与本地验证」？  
4. 下一两个迭代：默认是**扩壳**还是**加深核**？若 Freya 口头仍是「先弄得像完整 Web」，Agent 是否愿意用上面的 brief 拆分帮她对齐？  
5. 是否需要任何「大重构」？若需要，请写清缠死点；若不要，请写清「冻结壳 + 小步诚实化」是否足够。

## 请产品负责人确认

1. 是否认同「先核后壳」作为**默认构建顺序**（云端分发仍可保留，但不自动获得最高优先级）？  
2. 是否请你的 Agent 按上文清单做一次书面审视，并分享结论（可很短）？  
3. 「暂未开放」入口：维持展示路线图，还是收敛可见入口？  
4. 本地体验诚实化（不推 SIWC 404）可否作为日后独立小 PR，而不与大重构绑定？  
5. 本提案确认前是否仅停留在 `docs/proposals/`，确认后再酌情写入 `docs/DECISIONS.md`？
