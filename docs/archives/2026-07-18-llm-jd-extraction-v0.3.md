# LLM JD 结构化识别链路 V0.3

## 本次问题

第三条真实 JD 的开头是：

```text
邮箱有更正：
急急急招继任🔥TikTok AI 产品经理 日常实习base 北京
```

规则解析错误地把“邮箱有更正”当成公司，把包含急招、实习和地点的整行当成岗位名称，并漏掉北京。

该样例进一步证明：公司不一定直接出现，岗位和地点可能混在一句话里，通知语可能出现在开头。仅根据行序和关键词无法稳定完成语义识别。

## 预期结果

| 字段 | 结果 | 类型 |
| --- | --- | --- |
| 公司 | 字节跳动 | 语义推断：原文出现 TikTok |
| 岗位 | TikTok AI 产品经理 | 从混合标题中清洗 |
| 地点 | 北京 | 从 `base 北京` 提取 |
| 工作性质 | 实习 | 从“日常实习”判断 |
| 岗位类别 | 产品 | 从“产品经理”判断 |
| 投递邮箱 | 1371906748@qq.com | 原文直接提取 |

“字节跳动”并非原文逐字出现，因此确认页必须显示为“AI 语义推断”，不能显示成“原文直接提取”。

## 方案结论

JD 识别采用“LLM 主解析 + 程序证据校验 + 规则降级 + 用户确认”的组合，而不是继续用正则穷举所有写法。

### 1. LLM 结构化输出

服务端调用 OpenAI Responses API，并要求模型严格返回固定 JSON Schema。每个字段包含：

- `value`：标准化后的字段值；
- `evidence`：从 JD 中逐字复制的连续原文；
- `basis`：`explicit`、`inferred` 或 `unknown`；
- `confidence`：`high`、`medium` 或 `low`；
- `reason`：值与原文依据之间的简短解释。

OpenAI Structured Outputs 能保证输出符合指定 JSON Schema，但只能保证结构有效，不能自动保证字段事实正确，因此仍需后续证据校验与评测。

### 2. 证据校验

程序收到模型结果后逐字段检查：

1. `evidence` 必须真实存在于原始 JD；
2. 枚举值必须属于产品允许范围；
3. 邮箱必须通过格式校验；
4. `low` 或 `unknown` 字段不得自动写入；
5. 任何未通过校验的模型字段被丢弃，改用规则结果或留空。

自动测试已经覆盖：模型即使返回“腾讯”，只要引用的“腾讯招聘”不在原文中，系统就拒绝该字段。

### 3. 直接提取与语义推断分开

- 原文明写“北京”：标记为直接提取；
- 原文写“TikTok”，结果为“字节跳动”：标记为语义推断；
- 确认页对语义推断使用橙色标签，并展示引用与推断理由；
- 用户仍可修改所有字段，确认后才创建岗位记录。

### 4. 安全降级

模型密钥缺失、调用超时、模型拒绝或返回未通过校验时，系统自动降级为规则解析，同时明确提示用户重点核对推断字段，不会把规则结果冒充成 AI 结果。

## 已实现代码

- 新增服务端岗位识别接口；
- 使用 Responses API 的严格 JSON Schema 输出格式；
- 默认模型设为 `gpt-5.6-terra`，可通过环境变量替换；
- 模型请求设置 `store: false`；
- API 密钥只从服务端环境变量读取，不进入浏览器代码和 Git；
- LLM 使用者受邮箱允许名单限制，避免公开站点被任意调用产生费用；
- 客户端按钮改为“AI 理解岗位信息”；
- 确认页区分 AI 识别、规则降级、原文提取和语义推断；
- 新增证据验证与模型幻觉拒绝测试；
- 第三条真实 TikTok JD 已加入永久回归样例。
